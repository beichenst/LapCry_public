# LapCry 开发与验收规范

## 1. 文档目的

本文档定义 LapCry 从源码基线、功能改造、桌面封装、测试验证、打包发布到 GitHub 托管的全过程要求。开发过程中的每个阶段均以本文档为验收依据；实现与规范不一致时必须先修正实现，再进入下一阶段。

- 产品名称：LapCry
- 创作人信息：Bin9chn
- 源码基线：Apache-2.0 上游数据处理引擎 11.5.0
- 基线许可：Apache License 2.0
- 目标平台：Windows 10/11 x64
- 核心目标：在桌面 EXE 中保留上游全部操作能力，并提供重新设计的 UI、拖拽配方、自定义脚本、语言与主题切换。
- 基本原则：本地优先、离线优先、数据不出本机、功能可验证、异常可定位、构建可重复。

## 2. 功能范围

### 2.1 必须保留

1. 保留上游全部操作模块和配方执行语义。
2. 支持静态输入、文件输入、文件夹输入和多标签输入。
3. 支持操作搜索、分类浏览、双击添加、拖拽添加、拖拽排序、拖拽删除。
4. 支持操作参数编辑、默认值、选项、数值、文本、文件等参数类型。
5. 支持自动烘焙和手动烘焙。
6. 支持断点、单步执行、Fork、Register、Magic、Deep Link 等上游能力。
7. 支持配方保存、加载、删除、复制和导入导出。
8. 支持输入与输出字符编码、行尾格式、高亮关联和文件下载。
9. 支持二进制、文本、图片、音视频和结构化数据相关操作。
10. 支持上游 Node API 与浏览器 Worker 执行路径的测试。

### 2.2 必须改造

1. 产品名称、标题、关于信息、窗口标题和安装包元数据统一改为 LapCry。
2. 用户界面、EXE 元数据和发布品牌统一显示 Bin9chn；上游来源与 Apache 2.0 许可只保留在法律声明文件中。
3. UI 重新设计，采用清晰、克制、具备科技感的桌面工具风格。
4. 设置面板提供深色与浅色主题切换。
5. 设置面板提供中文与 English 界面切换。
6. 语言和主题偏好持久化，重启软件后保持。
7. UI、菜单、状态、提示、确认框、错误信息和设置项应随语言切换。
8. 上游操作名称与算法专有名词默认保留英文；允许通过本地翻译表覆盖常用分类和常用操作名称。
9. 支持自定义 JavaScript 函数作为配方操作，并纳入保存、加载、排序和删除流程。
10. 自定义脚本仅在本机 Worker 内执行，不向网络发送输入、脚本或结果。

### 2.3 明确不做

1. 不引入账号、云同步、遥测、在线翻译、在线更新检查等后台网络服务。
2. 不修改密码学算法结果以迁就 UI。
3. 不删除上游低频操作以减少体积。
4. 不以“网页快捷方式”代替独立 EXE。
5. 不把用户输入、配方或脚本上传到任何远程服务。
6. 不发布仅含源码 ZIP 的伪桌面版本。

## 3. 技术架构

### 3.1 运行架构

- 桌面壳：.NET 8 WinForms。
- 浏览器引擎：Microsoft WebView2。
- 前端：基于上游 Apache-2.0 源代码的 LapCry Web 构建产物，使用 Webpack。
- 本地服务：仅监听 `127.0.0.1` 的临时端口，用于提供静态资源和 Worker。
- 进程边界：WebView2 与本地静态服务均为本机进程，不开放局域网访问。
- 数据路径：输入、配方和结果只在 WebView2、Worker 与内存之间流转。
- 退出清理：程序退出时关闭本地监听器并释放 WebView2 资源。

### 3.2 源码边界

- `src/core/`：上游核心操作与 LapCry 执行引擎。
- `src/web/`：LapCry 前端界面、主题、语言资源和交互改造。
- `desktop/LapCry.Desktop/`：Windows 桌面壳与本地静态服务。
- `tests/`：上游功能回归测试和 LapCry 增量测试。
- `scripts/`：构建、打包、验收和发布辅助脚本。
- `artifacts/`：本地生成的可分发文件，不提交构建缓存。
- `LAPCRY_DEVELOPMENT_ACCEPTANCE.md`：本规范。

### 3.3 配置持久化

- Web 设置键：`lapcry.settings.v1`。
- 配方键：沿用上游本地存储格式，并提供迁移兼容。
- 自定义脚本键：`lapcry.customOperations.v1`。
- 主题值：`light`、`dark`。
- 语言值：`zh-CN`、`en-US`。
- 首次启动默认值：浅色主题、中文界面。

## 4. 开发流程

### 阶段 0：基线与来源确认

工作内容：

1. 获取经验证的上游 Apache-2.0 源码。
2. 确认版本、提交号、许可证和依赖完整性。
3. 执行一次原始安装、构建和测试，保存基线结果。
4. 记录上游源码地址、提交号和构建命令。

退出条件：

- 基线源码可构建。
- 基线核心测试通过，或所有失败项均有明确记录。
- Apache 2.0 许可和来源信息未被删除。

### 阶段 1：品牌与工程结构

工作内容：

1. 更新产品名、作者、描述、首页、仓库地址和包元数据。
2. 建立桌面壳项目。
3. 建立统一构建脚本和产物目录。
4. 添加 LapCry 图标和窗口资源。
5. 更新 README、关于页和第三方许可说明。

退出条件：

- 前端构建标题为 LapCry。
- EXE 元数据作者为 Bin9chn。
- 关于页、EXE 和发布品牌仅显示 LapCry、版本与 Bin9chn；法律声明集中于 LICENSE 与 THIRD_PARTY_NOTICES.md。

### 阶段 2：UI 重构

工作内容：

1. 重构顶部栏、操作区、配方区、输入输出区和状态栏。
2. 使用集中式 CSS 变量，统一颜色、边界、间距、字体和交互状态。
3. 创建深色和浅色两套完整变量。
4. 优化窄窗口、常规窗口和大窗口布局。
5. 保留拖拽热区、操作参数控件和上下文帮助。
6. 提供设置抽屉或设置弹窗，集中管理主题、语言、自定义函数和现有选项。
7. 提升空状态、加载状态、错误状态和运行中状态的辨识度。

退出条件：

- 1920x1080、1440x900、1280x720 三档窗口布局无重叠。
- 深色与浅色主题下文本、按钮、输入框、弹窗和操作卡片均可读。
- 拖拽添加与排序行为与上游一致。
- UI 无宣传页、无多余卡片嵌套、无装饰性渐变球体。

### 阶段 3：中英文切换

工作内容：

1. 建立集中式 i18n 资源文件。
2. 为标题、菜单、设置、按钮、状态、确认框、错误提示和主要空状态提供中英文。
3. 在设置中提供语言选择，并即时刷新可见文本。
4. 保存语言偏好，重新启动后恢复。
5. 对插件或操作参数中的技术名词采用一致性策略，不产生半中半英混乱。

退出条件：

- 中文和 English 可即时切换。
- 切换后主要界面无残留错误语言。
- 重新启动后语言偏好保持。
- 切换语言不改变当前输入、配方或输出。

### 阶段 4：自定义函数

工作内容：

1. 新增“自定义 JavaScript / Custom JavaScript”操作。
2. 支持函数名称、说明、参数定义和函数体编辑。
3. 支持将自定义函数加入配方、排序、保存和重复执行。
4. 自定义函数通过 Worker 执行，超时、异常和结果类型必须有明确提示。
5. 限制脚本访问网络和桌面文件系统，默认不允许主动联网。
6. 对危险输入和异常返回提供可见错误，不导致整个应用崩溃。

退出条件：

- 可以新增、编辑、删除、运行并持久化至少一个自定义函数。
- 自定义函数可与内置操作混合组成配方。
- 脚本异常不会使主界面失去响应。
- 重启后可加载之前保存的自定义函数。

### 阶段 5：桌面封装

工作内容：

1. 构建 LapCry 生产前端产物。
2. 将前端产物嵌入桌面发行目录。
3. WebView2 仅加载本机回环静态服务。
4. 处理窗口尺寸、最小尺寸、标题、图标、重载和退出行为。
5. 禁止外部任意导航、弹出窗口和新窗口劫持。
6. 对失效资源、端口占用、WebView2 缺失和启动异常提供清晰提示。
7. 生成可执行文件及必要的运行文件。

退出条件：

- 双击 EXE 可启动 LapCry。
- 无需浏览器手工打开网页。
- 断网后核心操作仍可运行。
- 退出后无残留监听端口或后台进程。
- 内存占用在验收阈值内。

### 阶段 6：完整测试

工作内容：

1. 执行上游操作测试。
2. 执行上游 Node API 测试。
3. 执行 LapCry 增量单元测试。
4. 执行 UI 功能和交互测试。
5. 执行主题、语言、自定义函数和持久化测试。
6. 执行 EXE 启动、离线、退出和内存测试。
7. 对关键加密、编码、压缩、解析、拖拽和保存功能做抽样交叉验证。

退出条件：

- 所有阻断级缺陷关闭。
- 所有高价值路径测试通过。
- 失败测试有复现步骤、影响和处置结论。
- 形成测试记录与验收结论。

### 阶段 7：打包与 GitHub 发布

工作内容：

1. 生成版本号、校验文件和发布说明。
2. 生成 Windows x64 可分发压缩包。
3. 如条件允许，生成单文件自包含 EXE。
4. 初始化或规范 Git 仓库。
5. 创建公开 GitHub 仓库并推送源码。
6. 创建版本标签并上传构建产物。
7. README 提供下载、运行、构建、测试、许可和署名说明。

退出条件：

- GitHub 仓库可公开访问。
- 默认分支包含完整源码和规范文档。
- Release 包含可下载 EXE 或发布压缩包。
- 源码、二进制和许可证中的署名一致。
- 发布说明列出已知限制。

## 6. 性能与资源指标

| 指标 | 目标 | 阻断阈值 |
| --- | --- | --- |
| 空闲内存工作集 | 不高于 250 MB | 高于 350 MB 需优化或说明 |
| 冷启动到可交互 | 不高于 5 秒 | 高于 10 秒视为阻断 |
| 常规文本 Base64 往返 | 不高于 100 ms | 高于 500 ms 需调查 |
| 1 MB 文件加载 | 不高于 1 秒 | 高于 3 秒需调查 |
| 大量操作列表搜索 | 不高于 150 ms | 高于 500 ms 需优化 |
| 退出后残留进程 | 0 个 | 任何残留均视为阻断 |
| 非回环网络监听 | 0 个 | 任何公网或局域网监听均视为阻断 |

说明：内存阈值以 Windows 任务管理器“工作集”与进程组总占用为参考。WebView2 的子进程会计入总资源，验收报告必须同时记录桌面进程和 WebView2 进程组。

## 7. 测试策略

### 7.1 测试层级

1. 静态检查：ESLint、JSON 校验、资源引用检查。
2. 单元测试：操作逻辑、i18n 资源、主题映射、设置迁移。
3. 集成测试：配方执行、Worker、文件流、保存加载。
4. UI 测试：拖拽、参数、设置、主题、语言、自定义函数。
5. 桌面验收：EXE 启动、离线、退出、导航、内存。
6. 探索测试：随机组合现有操作，检查异常、死锁和输出错误。

### 7.2 测试数据

- 空输入。
- ASCII、中文、Emoji、组合 Unicode。
- 二进制随机字节。
- 大文本、大文件、多文件。
- 已知标准测试向量。
- 合法与非法 Base64、Hex、JSON、JWT、证书。
- 脚本正常、抛错、死循环、超大返回。
- 深色、浅色和中英文组合。

### 7.3 缺陷分级

- P0：无法启动、数据损坏、任意网络泄露、核心操作不可用。
- P1：主要流程失败、主题或语言切换不可用、自定义函数导致崩溃。
- P2：非关键操作异常、个别提示未翻译、局部布局问题。
- P3：纯视觉细节、低频边界差异。

发布阻断条件：存在任一 P0 或 P1；P2 必须记录并给出规避方案；P3 不阻断但进入发布说明。

## 9. 发布物要求

Release 至少包含：

- `LapCry-<version>-win-x64.zip`
- `LapCry.exe` 或发布目录
- `LICENSE`
- `THIRD_PARTY_NOTICES.md`
- `README.md`
- `SHA256SUMS.txt`
- 发布说明

发布说明必须包含：

- 版本号和发布日期。
- 上游 Apache-2.0 引擎版本与提交号。
- 新增、修改、修复内容。
- 已知问题。
- 运行要求。
- 校验方式。
- Bin9chn 产品署名，以及法律文件中的第三方来源声明。

## 10. Git 与 GitHub 规范

1. 默认分支使用 `main`。
2. 提交信息使用简洁英文或中文，必须能说明变更目的。
3. 大体积构建缓存、`node_modules`、`bin`、`obj` 不提交。
4. 发布二进制通过 GitHub Release 上传，不直接塞入普通提交。
5. 上传前执行敏感信息扫描。
6. 不提交 token、cookie、私钥、浏览器缓存或用户配方。
7. README 必须提供可复现的构建步骤。
8. 仓库描述明确写出 LapCry 与 Bin9chn。
9. 未经明确授权，不使用用户其它仓库或删除已有内容。

## 11. 最终验收结论格式

最终报告必须逐项给出：

| 类别 | 结果 | 证据 |
| --- | --- | --- |
| 功能完整性 | 通过/部分通过/失败 | 操作数量、测试结果 |
| 拖拽配方 | 通过/部分通过/失败 | UI 测试与截图 |
| 自定义函数 | 通过/部分通过/失败 | 保存、运行、异常测试 |
| 中英文切换 | 通过/部分通过/失败 | 切换与重启记录 |
| 深色/浅色主题 | 通过/部分通过/失败 | 切换与重启记录 |
| EXE 启动 | 通过/部分通过/失败 | 进程与截图 |
| 离线运行 | 通过/部分通过/失败 | 网络禁用测试 |
| 内存 | 实测值 | 进程组统计 |
| 完整测试 | 通过/部分通过/失败 | 命令与摘要 |
| GitHub 上传 | 通过/部分通过/失败 | 仓库与 Release 链接 |

最终结论仅允许以下三种：

- 通过：无 P0/P1，P2 已记录，核心验收矩阵全部通过。
- 有条件通过：无 P0/P1，少量非核心项未完成且已有明确限制。
- 不通过：存在 P0/P1，或核心能力、拖拽、自定义、语言、主题、EXE、发布任一关键项失败。

## 12. 变更控制

1. 新需求必须回写本文档并增加验收项。
2. 与上游算法行为冲突时，以标准测试向量和上游测试为准。
3. 与 UI 设计偏好冲突时，以可用性、可读性和稳定性优先。
4. 与许可证冲突时，停止发布并修正。
5. 任何跳过测试的决定都必须记录原因、风险和受影响范围。
